# Event Model

## 1. Purpose

This document defines the business events generated by the **Banking Simulator** and processed by the **Enterprise Banking Data Platform**.

The event model provides a consistent contract between the synthetic banking environment, the transaction generator, the streaming ingestion layer, and the downstream Snowflake data platform.

The primary business event in the platform is the **TransactionOccurred** event.

Each transaction event represents a single financial occurrence and is treated as an immutable event.

---

# 2. Primary Business Event

## TransactionOccurred

A `TransactionOccurred` event represents a financial transaction that has occurred within the simulated banking environment.

The event contains the information required to identify:

* The transaction
* The participating accounts
* The merchant, where applicable
* The transaction amount
* The currency
* The transaction type
* The transaction status
* The time at which the transaction occurred

Examples of transaction activity include:

* Purchases
* Transfers
* ATM withdrawals
* Deposits
* Other configured banking transactions

The simulator generates these events using the existing customers, accounts, and merchants maintained within the simulated banking state.

---

# 3. Event Contract

The transaction event contains the following core attributes.

| Field                    | Required    | Description                              |
| ------------------------ | ----------- | ---------------------------------------- |
| `transaction_id`         | Yes         | Unique identifier for the transaction    |
| `source_account_id`      | Conditional | Account from which funds originate       |
| `destination_account_id` | Conditional | Account receiving funds                  |
| `merchant_id`            | Conditional | Merchant associated with the transaction |
| `amount`                 | Yes         | Monetary transaction amount              |
| `currency`               | Yes         | Currency associated with the transaction |
| `transaction_type`       | Yes         | Type of banking transaction              |
| `transaction_timestamp`  | Yes         | Time at which the transaction occurred   |
| `status`                 | Yes         | Current transaction status               |

### Conditional Fields

Not every transaction requires every participant.

For example:

```text
TRANSFER
    │
    ├── source_account_id
    └── destination_account_id
```

Whereas a merchant purchase may be represented as:

```text
PURCHASE
    │
    ├── source_account_id
    └── merchant_id
```

This allows the same event contract to represent different types of banking activity.

---

# 4. Supported Transaction Types

The simulator supports multiple transaction types.

| Transaction Type | Description                        |
| ---------------- | ---------------------------------- |
| `PURCHASE`       | Payment made to a merchant         |
| `TRANSFER`       | Funds transferred between accounts |
| `ATM_WITHDRAWAL` | Funds withdrawn through an ATM     |

The simulator can be extended with additional transaction types as new business scenarios are introduced.

The transaction generator determines the appropriate participants and transaction attributes based on the selected transaction type.

---

# 5. Transaction Status

A transaction can have one of the following statuses:

| Status      | Description                                      |
| ----------- | ------------------------------------------------ |
| `PENDING`   | Transaction has been initiated but not completed |
| `COMPLETED` | Transaction completed successfully               |
| `FAILED`    | Transaction failed                               |
| `REVERSED`  | Previously completed transaction was reversed    |

The status is part of the event because downstream processing and analytics may need to distinguish successful transactions from failed or reversed activity.

---

# 6. Banking Channels

Transactions may originate from different banking channels.

| Channel          | Description                |
| ---------------- | -------------------------- |
| `ATM`            | Automated Teller Machine   |
| `MOBILE_APP`     | Mobile banking application |
| `ONLINE_BANKING` | Internet banking           |
| `BRANCH`         | Physical bank branch       |
| `POS`            | Point-of-Sale terminal     |

The channel identifies the originating banking interface through which the transaction was generated.

---

# 7. Event Generation

Transaction events are generated by the Banking Simulator.

The simulator first establishes the banking environment:

```text
Customers
    │
    ▼
Accounts
    │
    ├──────────────► Merchants
    │
    ▼
Transaction Generator
```

The transaction generator then selects existing entities from the simulator state and creates a transaction event.

```text
Simulator State
      │
      ▼
Transaction Generator
      │
      ▼
TransactionOccurred
```

This ensures that transaction events maintain relationships with the simulated banking entities.

---

# 8. Event Processing

Once a transaction event has been generated, it enters the Enterprise Banking Data Platform.

For the streaming workload, the event is delivered using **Snowpipe Streaming**.

The processing flow is:

```text
TransactionOccurred
        │
        ▼
Banking Simulator
        │
        ▼
Snowpipe Streaming SDK
        │
        ▼
Snowflake RAW
        │
        ▼
BRONZE
        │
        ▼
SILVER
        │
        ▼
DATA VAULT 2.0
        │
        ▼
GOLD / ANALYTICS
```

Snowflake Streams and Tasks are then used to process newly arriving records incrementally through the downstream layers.

---

# 9. Initial Load

The event model is also used conceptually during the initial dataset generation.

The initial generator creates approximately:

* 100,000 customers
* 100,000 accounts
* 10,000 merchants
* 1,000,000 transactions

These historical transactions establish the initial state of the platform.

The initial data follows:

```text
Initial Transaction Data
        │
        ▼
       RAW
        │
        ▼
     BRONZE
        │
        ▼
     SILVER
        │
        ▼
 DATA VAULT 2.0
```

The streaming phase then adds new `TransactionOccurred` events to the existing platform.

---

# 10. Event Lifecycle

The complete lifecycle of a transaction event is:

```text
Business Transaction
        │
        ▼
TransactionOccurred Created
        │
        ▼
Banking Simulator
        │
        ▼
Snowpipe Streaming
        │
        ▼
Snowflake RAW
        │
        ▼
Bronze Transformation
        │
        ▼
Silver Transformation
        │
        ▼
Data Vault 2.0
        │
        ▼
Analytics / Monitoring
        │
        ▼
Suspicious Transaction Alert
```

The event itself remains immutable throughout this process.

Downstream layers may transform or model the event, but they do not modify the original business occurrence.

---

# 11. Event Immutability

A transaction event represents something that happened.

Therefore, the event should be treated as immutable.

```text
Transaction Event
       │
       ▼
     INSERT
       │
       ▼
Historical Record
```

Rather than modifying the original event, subsequent business activity can be represented through new events.

This approach is particularly useful for transaction histories, auditing, and Data Vault modeling.

---

# 12. Relationship to Data Vault 2.0

The event model maps naturally to the Data Vault 2.0 architecture.

The transaction's business identifier is represented by the Transaction Hub.

Relationships between the transaction and other business entities are represented by Links.

Descriptive transaction attributes are represented by Satellites.

```text
Transaction Event
       │
       ▼
Transaction Business Key
       │
       ▼
HUB_TRANSACTION
       │
       ▼
LINK_ACCOUNT_TRANSACTION
       │
       ▼
SAT_TRANSACTION
```

This allows the original transaction event to be transformed into an enterprise-oriented historical model while maintaining traceability back to the source event.

---

# 13. Suspicious Transaction Events

The event model also supports transaction-monitoring scenarios.

The simulator deliberately generates a small percentage of high-value transactions for anomaly and alert testing.

Currently, approximately **3% of transactions** may be generated within the suspicious high-value range:

```text
100,000 – 200,000
```

These events pass through the normal ingestion and transformation pipeline.

Once they reach the transaction Satellite, Snowflake Alert functionality can identify transactions meeting the configured threshold.

```text
TransactionOccurred
        │
        ▼
Snowpipe Streaming
        │
        ▼
RAW → BRONZE → SILVER
        │
        ▼
Data Vault
        │
        ▼
SAT_TRANSACTION
        │
        ▼
Suspicious Transaction Alert
        │
        ▼
Alert Log / Notification
```

This demonstrates how operational monitoring can be built directly on top of the data platform.

---

# 14. Technology Independence

The event model describes the **business event**, not the technology used to transport it.

The same `TransactionOccurred` event can theoretically be delivered through different ingestion mechanisms.

For example:

```text
                    TransactionOccurred
                           │
             ┌─────────────┴─────────────┐
             │                           │
       Initial Load                 Streaming
             │                           │
       Batch/File Load           Snowpipe Streaming
             │                           │
             └─────────────┬─────────────┘
                           ▼
                       Snowflake
```

The event contract therefore remains independent of the transport mechanism.

The current implementation uses **Snowpipe Streaming** for continuous transaction ingestion.

---

# 15. Extensibility

The event model is designed to support future transaction types without requiring a redesign of the entire platform.

New transaction types can be introduced by extending the transaction-generation and business-rule components.

For example:

```text
Current
├── PURCHASE
├── TRANSFER
└── ATM_WITHDRAWAL

Future
├── DEPOSIT
├── LOAN_PAYMENT
├── BILL_PAYMENT
└── CARD_PAYMENT
```

The core event structure remains consistent while individual transaction types determine which fields are applicable.

---

# 16. Design Principles

The event model follows these principles:

### Single Business Occurrence

Each event represents one business transaction.

### Immutability

Events represent historical occurrences and are not updated after creation.

### Technology Independence

The event contract is independent of the underlying ingestion mechanism.

### Consistent Contract

The same event structure is used throughout the simulator and downstream platform.

### Referential Integrity

Transaction participants reference entities that exist within the simulated banking environment.

### Extensibility

New transaction types and business scenarios can be introduced without redesigning the entire event model.

### Traceability

Each transaction contains a unique identifier that allows the event to be traced through RAW, Bronze, Silver, and Data Vault layers.

```text
             └──────────────┬──────────────┘
                            ▼
                         RAW
                            │
                            ▼
                         BRONZE
                            │
                            ▼
                         SILVER
                            │
                            ▼
                    DATA VAULT 2.0
                            │
              ┌─────────────┴─────────────┐
              │                           │
              ▼                           ▼
          ANALYTICS              TRANSACTION ALERT
                                          │
                                          ▼
                                  ALERT LOG /
                                  NOTIFICATION
```

The **TransactionOccurred event is therefore the central business contract connecting the Banking Simulator with the Enterprise Banking Data Platform**, while the downstream layers are responsible for ingestion, quality, transformation, enterprise modeling, analytics, and operational monitoring.
