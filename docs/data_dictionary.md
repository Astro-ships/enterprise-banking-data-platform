# Data Dictionary

## 1. Purpose

This document defines the business attributes used by the **Enterprise Banking Data Platform**.

It provides a consistent reference for:

* Attribute names
* Data types
* Required/optional status
* Business meaning
* Expected values
* Data quality considerations

The dictionary reflects the current implementation of the platform and its synthetic banking transaction simulator.

---

# 2. Transaction Event

The Transaction Event represents a financial transaction generated by the simulator and ingested into the platform.

| Field                    | Data Type     | Required    | Description                                               |
| ------------------------ | ------------- | ----------- | --------------------------------------------------------- |
| `transaction_id`         | VARCHAR       | Yes         | Unique business identifier for the transaction event.     |
| `source_account_id`      | VARCHAR       | Yes         | Account initiating the transaction.                       |
| `destination_account_id` | VARCHAR       | Yes         | Account receiving or associated with the transaction.     |
| `merchant_id`            | VARCHAR       | Conditional | Merchant associated with the transaction when applicable. |
| `amount`                 | FLOAT         | Yes         | Monetary value of the transaction.                        |
| `currency`               | VARCHAR       | Yes         | Currency associated with the transaction.                 |
| `transaction_type`       | VARCHAR       | Yes         | Type of financial transaction.                            |
| `transaction_timestamp`  | TIMESTAMP_NTZ | Yes         | Date and time when the transaction occurred.              |
| `status`                 | VARCHAR       | Yes         | Current status associated with the transaction event.     |

## Supported Transaction Types

The current simulator supports:

| Transaction Type | Description                         |
| ---------------- | ----------------------------------- |
| `PURCHASE`       | Payment made for goods or services. |
| `TRANSFER`       | Transfer of funds between accounts. |
| `ATM_WITHDRAWAL` | Cash withdrawal through an ATM.     |

The transaction generator may introduce suspicious high-value transactions independently of transaction type.

---

## Transaction Status

The simulator supports the following transaction statuses:

| Status      | Description                                         |
| ----------- | --------------------------------------------------- |
| `PENDING`   | Transaction has been initiated but not completed.   |
| `COMPLETED` | Transaction completed successfully.                 |
| `FAILED`    | Transaction failed to complete.                     |
| `REVERSED`  | Previously completed transaction has been reversed. |

# 3. Customer

Customer attributes describe the individuals or entities represented in the banking system.

| Field           | Data Type | Required | Description                                |
| --------------- | --------- | -------- | ------------------------------------------ |
| `customer_id`   | VARCHAR   | Yes      | Unique business identifier for a customer. |
| `customer_name` | VARCHAR   | Yes      | Full name of the customer.                 |
| `email`         | VARCHAR   | Yes      | Customer email address.                    |
| `phone`         | VARCHAR   | Yes      | Customer phone number.                     |
| `address`       | VARCHAR   | Yes      | Customer mailing address.                  |
| `date_of_birth` | DATE      | Yes      | Customer date of birth.                    |

The `customer_id` acts as the business key for `HUB_CUSTOMER`.

# 4. Account

Account attributes describe financial accounts associated with customers.

| Field              | Data Type | Required | Description                                   |
| ------------------ | --------- | -------- | --------------------------------------------- |
| `account_id`       | VARCHAR   | Yes      | Unique business identifier for the account.   |
| `account_type`     | VARCHAR   | Yes      | Type of banking account.                      |
| `account_status`   | VARCHAR   | Yes      | Current status of the account.                |
| `account_currency` | VARCHAR   | Yes      | Primary currency associated with the account. |
| `opened_date`      | DATE      | Yes      | Date on which the account was opened.         |

## Account Types

The simulator may generate account types such as:

* `CHECKING`
* `SAVINGS`
* `BUSINESS`

## Account Statuses

Supported account statuses include:

* `ACTIVE`
* `DORMANT`
* `CLOSED`

The `account_id` acts as the business key for `HUB_ACCOUNT`.

# 7. Link Attributes

The current implementation uses an Account–Transaction relationship.

## LINK_ACCOUNT_TRANSACTION

| Field                    | Data Type | Description                                                 |
| ------------------------ | --------- | ----------------------------------------------------------- |
| `ACCOUNT_TRANSACTION_HK` | VARCHAR   | Hash key representing the Account–Transaction relationship. |
| `ACCOUNT_HK`             | VARCHAR   | Hash key identifying the associated account.                |
| `TRANSACTION_HK`         | VARCHAR   | Hash key identifying the associated transaction.            |
| `LOAD_DATE`              | TIMESTAMP | Date and time when the relationship was loaded.             |
| `RECORD_SOURCE`          | VARCHAR   | Source from which the relationship was loaded.              |

The relationship hash key is derived from the source account and transaction identifiers.

Conceptually:

```text
source_account_id + transaction_id
              │
              ▼
             MD5
              │
              ▼
ACCOUNT_TRANSACTION_HK
```

# 11. Business Rules

The platform follows the following business rules.

### Transaction Identity

Every transaction is identified by a unique `transaction_id`.

### Account Association

Transactions are associated with source and destination accounts according to the transaction event generated by the simulator.

### Merchant Association

A merchant is associated with transactions where merchant information is applicable.

### Transaction History

Transactions are treated as business events and are not physically updated after ingestion.

### Data Vault Relationships

Business relationships are represented using Data Vault Links rather than duplicating relationship information across entity records.

### Historical Information

Descriptive history is preserved through Data Vault Satellites.

### Data Quality

Data quality processing occurs primarily in the Silver layer before records are loaded into the Data Vault.

---

# 12. Data Quality Scenarios

The simulator is designed to support imperfect source data so that the platform can demonstrate realistic data-engineering scenarios.

Potential scenarios include:

* Duplicate transaction events
* Missing optional attributes
* Invalid or unexpected values
* Non-standard currency representations
* Late-arriving events
* Out-of-order events
* High-value transactions
* Other intentionally introduced data-quality issues

These scenarios allow the Medallion Architecture to demonstrate how imperfect source data can be progressively validated and transformed.

---

# 13. Suspicious Transaction Data

The platform intentionally generates a small percentage of high-value transactions to demonstrate operational monitoring.

Approximately **3% of generated transactions** can be assigned a suspicious high-value amount.

These transactions are identified by the Snowflake Alert when:

```text
AMOUNT >= 100000
```

The monitoring flow is:

```text
Transaction Event
       │
       ▼
     RAW
       │
       ▼
    BRONZE
       │
       ▼
    SILVER
       │
       ▼
SAT_TRANSACTION
       │
       ▼
Snowflake Alert
       │
       ├──► Alert Log
       │
       └──► Notification
```

This demonstrates the integration of data ingestion, transformation, Data Vault modeling, and operational monitoring.
