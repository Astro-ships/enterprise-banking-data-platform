# ADR-003: Adopt a Hybrid Data Ingestion Strategy

## Status

Accepted

---

## Context

The Enterprise Banking Data Platform is being developed incrementally.

During the early stages of development, the primary objective is to design, validate, and test the complete data engineering pipeline before introducing real-time event ingestion.

The platform requires an ingestion strategy that supports rapid development while remaining compatible with the long-term architecture based on event-driven processing.

---

## Decision

The platform will adopt a hybrid data ingestion strategy consisting of two phases.

### Phase 1 – Batch File Ingestion

Synthetic banking events generated by the event generator will be exported as NDJSON files.

These files will be manually uploaded to an internal Snowflake Stage and loaded into the Bronze layer using `COPY INTO` commands.

This approach will be used during the initial development phase to validate:

* File formats.
* Table structures.
* Bronze layer ingestion.
* Silver transformations.
* Data Vault 2.0 modeling.
* Gold analytical models.

### Phase 2 – Streaming Ingestion

Once the batch pipeline has been validated, the platform will transition to real-time ingestion.

Banking events will be submitted through a REST API.

The API will insert incoming events directly into Snowflake.

Snowflake Streams will capture newly inserted records and drive downstream processing into the Medallion Architecture.

This architecture enables the platform to evolve from batch processing to near real-time data processing without requiring changes to downstream transformations.

---

## Rationale

Building the platform in two phases reduces implementation complexity while allowing each architectural layer to be independently validated.

Using staged files during early development provides several advantages:

* Easier debugging.
* Faster iteration.
* Repeatable testing.
* Simpler validation of transformations.

After the core pipeline is stable, replacing manual uploads with API-based ingestion introduces real-time capabilities while preserving the existing Bronze, Silver, Data Vault, and Gold layers.

This phased approach minimizes risk and reflects how many enterprise data platforms are introduced into production.

---

## Alternatives Considered

### Option 1 — Build Real-Time Ingestion First

The platform would immediately expose REST APIs and process events through Snowflake Streams.

**Advantages**

* Real-time architecture from the beginning.
* Eliminates temporary batch ingestion.

**Disadvantages**

* Higher implementation complexity.
* More difficult to debug.
* Requires multiple components before validating the core data pipeline.

---

### Option 2 — Batch Ingestion Only

The platform would permanently rely on manually uploaded files.

**Advantages**

* Simple implementation.
* Easy to maintain.

**Disadvantages**

* No real-time capabilities.
* Does not represent modern banking architectures.
* Cannot demonstrate streaming workflows.

---

### Option 3 — Hybrid Ingestion Strategy (Selected)

The platform begins with staged batch ingestion and later transitions to API-driven streaming ingestion.

**Advantages**

* Simplifies early development.
* Enables incremental delivery.
* Preserves downstream architecture.
* Supports both batch and streaming workloads.
* Closely reflects enterprise implementation strategies.

**Disadvantages**

* Requires maintaining two ingestion mechanisms during development.
* Additional migration effort when enabling streaming.

---

## Consequences

The initial implementation will use manually uploaded NDJSON files stored in an internal Snowflake Stage.

The Bronze layer will ingest these files using `COPY INTO`.

After validation of the complete Medallion Architecture and Data Vault 2.0 implementation, the ingestion layer will be upgraded to:

```
Event Generator
        │
        ▼
REST API
        │
        ▼
Snowflake Landing Table
        │
        ▼
Snowflake Stream
        │
        ▼
Bronze
        │
        ▼
Silver
        │
        ▼
Data Vault 2.0
        │
        ▼
Gold
```

This decision provides a clear migration path from batch processing to event-driven streaming while maintaining a consistent downstream architecture.
